LLM이 외부 도구를 사용할 수 있게 되면 단순한 답변 모델에서 작업을 수행하는 에이전트로 확장된다. 캘린더 일정을 만들고, 데이터베이스를 조회하고, 코드를 실행한 뒤 그 결과를 바탕으로 다음 행동을 결정할 수 있다.

하지만 모델이 JSON 형태의 도구 호출을 만들었다고 해서 사용자의 요청이 완료된 것은 아니다. 호출을 검증하고 실제 API를 실행하며, 결과를 확인하고, 적절한 시점에 멈추는 시스템이 필요하다.

```text
사용자 요청
    ↓
LLM의 도구 선택과 인자 생성
    ↓
Runtime의 검증과 실제 실행
    ↓
도구 결과 관찰
    ↓
다음 행동 또는 최종 답변
```

이 글에서는 Function Calling과 ReAct를 이 흐름 안에서 연결하고, 에이전트가 정말 잘 작동하는지 평가하는 방법까지 정리한다.

## 1. Function Calling은 실행이 아니라 실행 요청이다

Function Calling에서는 모델에 사용할 수 있는 도구의 이름, 설명, 입력 스키마를 제공한다. 모델은 사용자의 자연어 요청을 보고 어떤 도구를 어떤 인자로 호출할지 구조화된 형태로 출력한다.

> 사용자: “내일 오후 3시에 회의 잡아줘.”

캘린더 도구의 입력 스키마가 다음과 같다고 하자.

```json
{
  "name": "create_calendar_event",
  "arguments": {
    "title": "회의",
    "start_time": "2026-08-01T15:00:00+09:00"
  }
}
```

LLM의 역할은 `내일`, `오후 3시`, `회의`라는 표현을 도구가 이해하는 필드와 값으로 바꾸는 것이다. 이를 argument extraction 또는 slot filling의 관점에서 볼 수 있다.

여기서 중요한 경계가 있다.

- **LLM**은 도구를 선택하고 인자를 제안한다.
- **Runtime**은 스키마와 권한을 검증하고 API를 호출한다.
- **외부 시스템**은 실제 상태를 변경하고 결과를 반환한다.

모델이 만든 JSON은 신뢰할 수 있는 실행 결과가 아니라 검증이 필요한 제안이다. 일정 생성이 실제로 성공했는지는 캘린더 API의 응답이나 이후 시스템 상태로 확인해야 한다.

## 2. 좋은 Tool Schema가 좋은 호출을 만든다

도구 설명과 스키마가 모호하면 모델도 안정적으로 호출하기 어렵다. 좋은 Tool Schema는 다음 정보를 명확히 표현해야 한다.

- 도구가 수행하는 일과 수행하지 않는 일
- 필수 인자와 선택 인자
- 날짜, 금액, 식별자 등의 형식
- 허용되는 enum 값과 범위
- 실행에 필요한 권한과 중요한 부작용
- 실패 시 반환하는 오류 구조

예를 들어 `time`이라는 문자열 하나보다 timezone이 포함된 ISO 8601 형식의 `start_time`을 요구하는 편이 명확하다. `user_id`도 자유 텍스트가 아니라 시스템에서 확인된 식별자만 받도록 제한해야 한다.

### 정보가 부족하면 호출보다 질문이 먼저다

“회의 잡아줘”라는 요청에는 날짜, 시간, 참석자가 없다. 모델이 값을 추측해 일정을 생성하면 형식은 맞아도 목표는 틀릴 수 있다.

```text
필수 슬롯 확인
    ├─ 모두 있음 → 도구 호출 후보 생성
    └─ 일부 없음 → 사용자에게 필요한 정보 질문
```

모든 누락 정보를 반드시 한 번에 물어야 하는 것은 아니다. 기본값을 써도 되는 필드와 명시적 확인이 필요한 필드를 제품 정책으로 구분해야 한다. 결제, 삭제, 외부 메시지 전송처럼 영향이 큰 행동은 실행 직전 확인 절차도 필요할 수 있다.

## 3. Runtime이 반드시 책임져야 하는 것

도구 실행기는 모델과 외부 시스템 사이의 안전 경계다. 최소한 다음 역할을 담당해야 한다.

1. JSON과 스키마를 검증한다.
2. 인증과 권한을 확인한다.
3. 요청 제한, timeout, 재시도 정책을 적용한다.
4. 외부 API 오류를 구조화해 모델에 돌려준다.
5. 실행 결과와 상태 변경을 기록한다.

모델의 인자가 스키마를 통과했다고 해서 의미적으로 안전한 것은 아니다. `transfer_amount`가 숫자여도 사용자의 한도를 초과할 수 있고, 파일 경로가 문자열이어도 접근 허용 범위 밖일 수 있다. 형식 검증 뒤에 도메인 규칙과 권한 검증이 이어져야 한다.

도구가 반환한 텍스트도 신뢰할 수 없는 입력으로 취급해야 한다. 웹페이지나 문서의 내용이 에이전트의 상위 지시를 바꾸거나 다른 도구를 마음대로 호출하게 해서는 안 된다.

## 4. ReAct: 행동 결과를 보고 다음 행동을 정하기

Function Calling이 한 번의 도구 호출 형식을 설명한다면 ReAct는 관찰을 반복하며 문제를 푸는 실행 패턴이다.

```text
Reason → Act → Observe → Reason → Act → Observe → ... → Answer
```

- **Reason**: 현재 상태에서 필요한 다음 단계를 판단한다.
- **Act**: 도구를 호출하거나 사용자에게 질문한다.
- **Observe**: 도구의 결과와 오류를 확인한다.

핵심은 첫 계획을 무조건 끝까지 실행하는 것이 아니라, 행동의 결과에 따라 계획을 수정한다는 점이다. 검색 결과가 부족하면 질의를 바꾸고, API가 실패하면 오류 종류에 맞게 재시도하며, 이미 목표가 달성됐다면 더 호출하지 않고 멈춘다.

ReAct를 구현한다고 모델의 모든 내부 추론을 사용자나 로그에 그대로 노출할 필요는 없다. 운영 시스템에서는 도구 호출, 관찰 결과, 상태 전이, 간결한 결정 근거처럼 감사와 디버깅에 필요한 구조화된 정보만 기록하는 편이 안전하다.

## 5. 종료 조건: 에이전트는 언제 멈춰야 하는가

도구를 호출할 수 있는 능력만큼 중요한 것이 멈추는 능력이다. 종료 조건이 약하면 같은 검색을 반복하거나 이미 성공한 작업을 다시 실행해 비용과 위험을 키울 수 있다.

에이전트는 다음을 확인해야 한다.

- 사용자의 목표가 실제로 충족됐는가?
- 필요한 도구 실행이 성공했는가?
- 결과를 시스템 상태나 신뢰 가능한 응답으로 검증했는가?
- 남은 정보 부족이 추가 호출로 해결 가능한가?
- 다음 행동의 기대 가치가 비용과 위험보다 큰가?

제품에서는 의미 기반 판단만 믿지 말고 기계적인 제한도 함께 둔다.

```text
max_steps
max_tool_calls
max_retries_per_tool
overall_timeout
token_or_cost_budget
```

한도에 도달했을 때는 성공한 척 답하지 말고, 완료된 부분과 완료하지 못한 부분, 마지막 오류를 명확히 전달해야 한다.

## 6. 재시도와 멱등성

네트워크 timeout이 발생했다고 작업이 실패한 것은 아닐 수 있다. 서버에서는 일정 생성에 성공했지만 응답만 유실됐을 수도 있다. 이때 같은 요청을 다시 보내면 일정이 두 개 생긴다.

멱등성 키는 같은 논리적 요청의 중복 실행을 막는 대표적인 방법이다.

```json
{
  "idempotency_key": "op_7f3c2a91",
  "title": "회의",
  "start_time": "2026-08-01T15:00:00+09:00"
}
```

서버는 같은 키로 받은 요청을 새 작업으로 실행하지 않고 이전 결과를 반환할 수 있다. 키는 논리적 작업을 처음 시작할 때 한 번 만들고 저장한 뒤, **그 작업의 재시도에서는 동일하게 재사용**해야 한다. 사용자가 별개의 동일한 일정을 다시 요청했다면 새로운 작업이므로 새 키를 사용한다.

재시도 정책도 오류에 따라 달라야 한다.

- 일시적인 네트워크 오류와 5xx는 제한적으로 재시도할 수 있다.
- 잘못된 인자나 권한 부족은 같은 요청을 반복해도 해결되지 않는다.
- 상태 변경 API는 멱등성 보장이나 실행 상태 조회 없이 무작정 재시도하면 안 된다.

## 7. 에이전트 평가는 정답률 하나로 끝나지 않는다

같은 문제를 두 에이전트가 모두 해결했더라도 성능이 완전히 같다고 볼 수 없다. 한 에이전트가 세 번의 호출로 끝냈고 다른 에이전트가 스무 번의 호출과 두 번의 위험한 시도를 거쳤다면 운영 품질은 다르다.

에이전트 Evaluation의 주요 축은 다음과 같다.

| 평가 축 | 핵심 질문 | 예시 지표 |
| --- | --- | --- |
| Task success | 사용자 목표를 달성했는가? | 성공률, 완료율 |
| Correctness | 답과 행동이 정확한가? | 정답률, 상태 일치율 |
| Efficiency | 얼마나 적은 자원으로 해결했는가? | 단계 수, 토큰, 비용, 지연 시간 |
| Reliability | 반복 실행과 예외에서 안정적인가? | 성공률 분산, 오류 회복률 |
| Safety | 권한 밖 행동과 위험한 실행을 피했는가? | 정책 위반률, 차단 성공률 |

이 지표를 무조건 평균 내면 중요한 실패가 가려질 수 있다. 예를 들어 안전성은 낮은 비용으로 상쇄할 수 있는 항목이 아니다. 제품 요구에 따라 최소 통과 기준을 먼저 두고, 그 안에서 비용과 품질을 비교하는 편이 적합하다.

## 8. Outcome과 Trajectory를 함께 평가하기

에이전트 평가는 최종 결과와 그 과정으로 나눌 수 있다.

### Outcome Evaluation

최종 목표가 달성됐는지 본다.

- 일정이 정확한 시간에 한 번만 생성됐는가?
- 사용자가 요청한 파일이 올바른 위치에 저장됐는가?
- 최종 답변이 시스템의 실제 상태와 일치하는가?

가능하면 자연어 답변보다 외부 시스템의 상태를 직접 확인하는 것이 강한 증거다.

### Trajectory Evaluation

목표까지 가는 행동 경로가 적절했는지 본다.

- 올바른 도구를 선택했는가?
- 필요한 인자를 확인한 뒤 호출했는가?
- 불필요하거나 중복된 호출이 있었는가?
- 오류를 보고 적절히 복구했는가?
- 위험한 행동 전에 확인과 권한 검사가 있었는가?

정답을 우연히 맞힌 에이전트와 재현 가능한 절차로 해결한 에이전트를 구분하려면 Trajectory 평가가 필요하다. 다만 하나의 이상적인 경로만 정답으로 강제하면 유효한 다른 해결책을 오답 처리할 수 있으므로, 필수 조건과 허용 가능한 변형을 나눠야 한다.

## 9. 어떤 평가 방법을 사용할 것인가

평가 방법마다 잘 판단하는 대상이 다르다.

### 실행 기반 평가

실제 시스템 상태를 검사한다. 일정 생성, 데이터베이스 갱신, 테스트 통과처럼 명확한 작업에서 가장 직접적이다. 가능하다면 sandbox나 격리된 테스트 환경에서 실행해야 한다.

### 규칙 기반 평가

스키마 준수, 필수 도구 호출, 금지된 인자, 단계 수 제한처럼 기계적으로 판단할 수 있는 조건에 적합하다. 빠르고 재현성이 높지만 의미적 품질을 모두 평가하지는 못한다.

### 정답 기반 평가

예상 답이나 기대 상태와 비교한다. 수학 문제, 정보 추출, 코드 테스트처럼 정답을 정의할 수 있을 때 유용하다.

### LLM-as-a-Judge

다른 LLM에 정확성, 유용성, 명료성 등을 채점하게 한다. 대량의 열린 형태 답변을 빠르게 평가할 수 있지만 위치 편향, 길이 편향, 자기 선호, 평가 프롬프트 민감성이 있다. 절대적인 정답 판정기가 아니라 사람이 검토할 대상을 넓게 선별하는 보조 평가자로 보는 편이 좋다.

### 사람 평가

정책과 품질의 경계 사례, 고위험 작업, 주관적 사용자 경험을 판단하는 데 필요하다. 비용이 크므로 자동 평가에서 불확실하거나 중요한 사례를 우선 샘플링하는 방식이 현실적이다.

평가 수단을 단순히 한 줄로 서열화하기보다 질문에 맞춰 조합해야 한다.

```text
실행 성공 여부 → 시스템 상태 검사
도구 호출 규칙 → 규칙 기반 검사
답변의 의미 품질 → 정답 비교 + LLM judge + 사람 검토
```

## 10. 실전 평가 세트 만들기

좋은 평가 세트는 정상적인 요청만 모으지 않는다. 실제 실패가 발생하는 경계를 포함해야 한다.

1. 도구가 필요 없는 단순 질문
2. 하나의 도구로 끝나는 정상 요청
3. 필수 정보가 빠진 요청
4. 여러 도구를 순서대로 사용해야 하는 요청
5. API timeout과 일시적 오류
6. 권한 부족과 정책 위반 요청
7. 같은 작업의 중복 실행 위험
8. 도구 결과에 잘못되거나 악의적인 텍스트가 포함된 경우
9. 답할 근거가 없어 중단해야 하는 경우

각 사례에는 기대하는 최종 상태, 허용되는 도구 호출, 금지 행동, 비용 한도, 평가 방법을 함께 정의한다. 모델이나 프롬프트를 바꿀 때 동일한 평가 세트를 반복 실행하면 개선과 회귀를 비교할 수 있다.

## 11. 신뢰할 수 있는 에이전트의 전체 구조

원문의 내용을 시스템 관점에서 연결하면 다음과 같다.

```text
1. 사용자 목표와 권한 확인
2. 필요한 정보가 부족하면 질문
3. LLM이 Tool Schema에 맞는 호출 제안
4. Runtime이 스키마·권한·정책 검증
5. 멱등성과 timeout을 적용해 도구 실행
6. 결과를 관찰하고 실제 상태 확인
7. 목표 달성 시 종료, 아니면 제한 안에서 다음 행동
8. Outcome과 Trajectory 로그를 평가
```

결론적으로 LLM 에이전트의 품질은 모델의 추론 능력만으로 결정되지 않는다. **모델은 행동을 제안하고, Runtime은 안전하게 실행하며, Evaluation은 목표가 실제로 달성됐는지 증명한다.** 이 세 경계를 분리할수록 실패 원인을 찾기 쉽고, 더 안전하고 재현 가능한 에이전트를 만들 수 있다.
