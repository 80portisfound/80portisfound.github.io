코딩 에이전트의 발전 속도를 보면 이런 질문이 자연스럽게 떠오른다.

> 피지컬 AI 시대에도 시스템 프로그래밍을 공부해야 할까?

이 질문에 답하려면 먼저 더 근본적인 질문을 던져야 한다. AI가 코드를 작성하는 지금도 개발자는 필요한가?

좋은 코딩 에이전트는 요구사항을 정리하고, 여러 파일을 수정하고, 테스트를 실행하며, 때로는 사람이 작성한 것보다 더 일관된 코드를 만든다. 충분한 맥락과 명확한 평가 기준이 주어지면 작은 서비스 하나를 거의 끝까지 구현하기도 한다. 그렇다면 코드 작성과 아키텍처 설계까지 AI가 맡게 될 때 개발자의 경쟁력은 어디에서 나올까?

내 결론부터 말하면 개발자는 여전히 필요하고, 시스템 프로그래밍은 오히려 더 중요해진다. AI의 능력은 물리적 자원 위에서 구현되며, 그 자원을 어떻게 배치하고 관리하느냐가 실제 시스템의 성능과 비용을 결정하기 때문이다.

## LLM의 똑똑함은 물리적 자원을 사용한다

LLM은 많은 지식을 압축해 두고 도구와 검색을 연결해 다양한 문제를 해결한다. 겉으로 보면 소프트웨어만의 능력처럼 보이지만, 그 동작은 GPU 연산과 메모리, 네트워크, 스토리지 위에서 이루어진다.

대표적인 예가 KV 캐시다. Transformer가 새로운 토큰을 생성할 때 각 레이어의 Self-Attention은 이전 토큰들의 Key와 Value를 참조한다. 이전 토큰에 대한 Key와 Value를 매번 다시 계산하는 대신 한 번 계산한 값을 저장해 두고 재사용하면 중복 연산을 크게 줄일 수 있다.

```text
이전 토큰의 Key·Value를 다시 계산
             ↓
Key·Value를 저장하고 다음 디코딩 단계에서 재사용
             ↓
연산량 감소, 메모리 사용량 증가
```

KV 캐시는 전형적인 시스템 트레이드오프를 보여 준다.

> 다시 계산할 것인가, 저장해 둘 것인가?

캐시가 존재하는 이유가 바로 여기에 있다. 연산을 줄이는 대신 저장 공간과 데이터 이동 비용을 지불한다.

KV 캐시에 필요한 메모리는 모델 구조에 따라 달라지지만 대략 다음 요소에 비례한다.

```text
KV cache bytes
≈ 2 × layer 수 × token 수 × KV head 수
  × head dimension × dtype bytes × batch size
```

앞의 `2`는 Key와 Value 두 종류를 뜻한다. GQA나 MQA처럼 Query Head보다 KV Head 수를 줄이는 구조는 이 메모리 사용량을 낮춘다. 반대로 대화가 길어지고 동시에 처리하는 요청이 많아지면 KV 캐시가 빠르게 커진다.

LLM이 긴 대화를 기억한다는 것은 추상적인 표현이 아니다. 서비스를 제공하는 시스템 입장에서는 더 많은 토큰의 상태를 메모리에 유지한다는 뜻이다. 컨텍스트 길이, 배치 크기, 동시 사용자 수 사이에서 계속 균형을 잡아야 하는 이유다.

Transformer와 KV 캐시의 기본 구조는 [Transformer 핵심 원리](/blog/transformer-fundamentals/)에서 더 자세히 다뤘다.

## HBM과 메모리 대역폭이 중요한 이유

KV 캐시는 보통 GPU의 HBM(High Bandwidth Memory)에 둔다. HBM은 용량도 중요하지만 이름 그대로 높은 대역폭을 제공한다는 점이 핵심이다.

LLM 추론의 모든 구간이 같은 특성을 가지는 것은 아니다. 긴 입력을 한꺼번에 처리하는 Prefill은 병렬 연산량이 많아 연산 성능의 영향을 크게 받는다. 반면 토큰을 하나씩 생성하는 Decode, 특히 배치가 작을 때는 모델 가중치와 KV 캐시를 반복해서 읽어야 하므로 메모리 대역폭의 영향을 크게 받는 경우가 많다.

```text
Prefill
  - 긴 입력 토큰을 병렬 처리
  - 상대적으로 연산 집약적

Decode
  - 토큰을 한 번에 하나씩 생성
  - 작은 배치에서는 메모리 대역폭의 영향이 큼
```

양자화가 추론 속도에 도움이 되는 이유도 여기에 있다. 낮은 비트 수로 가중치를 표현하면 정확도와 커널 지원이라는 조건이 붙지만, 메모리 사용량과 매 단계에서 읽어야 할 바이트 수를 줄일 수 있다. 효과는 하드웨어, 배치 크기, 양자화 방식에 따라 달라지지만 단순히 산술 연산이 줄어드는 문제만은 아니다.

HBM이 부족할 때 KV 캐시 일부를 CPU 메모리나 SSD로 내리는 오프로딩도 생각할 수 있다. 하지만 데이터를 GPU 밖으로 옮기는 순간 PCIe나 NVLink 대역폭, 스토리지 지연시간이라는 새로운 병목이 생긴다.

```text
GPU HBM
  ↕ 빠르지만 작고 비쌈
CPU DRAM
  ↕ 더 크지만 GPU와의 전송 비용 발생
SSD
  ↕ 훨씬 크지만 지연시간 증가
```

결국 문제는 “메모리를 더 사면 되는가?”에서 끝나지 않는다. 어떤 데이터를 어느 계층에 얼마나 오래 둘 것인지, 언제 이동시키고 언제 버릴 것인지 결정해야 한다. 운영체제가 오랫동안 다뤄온 메모리 계층과 캐시 관리의 문제다.

## 에이전트는 컨텍스트를 더 빠르게 만든다

코딩 에이전트는 사람과 한 번씩 대화하는 챗봇보다 훨씬 빠르게 컨텍스트를 쌓는다. 계획을 만들고, 파일을 읽고, 도구를 호출하고, 실행 결과를 관찰한 뒤 다시 행동하는 루프를 반복하기 때문이다.

```text
Reasoning
  → Tool Call
  → Observation
  → 다음 Reasoning
  → 새로운 Tool Call
```

파일 내용, 터미널 출력, 테스트 로그가 대화에 계속 추가된다. 에이전트가 오래 작업할수록 모델에 전달할 컨텍스트와 KV 캐시의 부담도 커진다. 모든 기록을 무조건 유지하면 비용이 증가하고, 너무 공격적으로 버리면 중요한 제약을 잊는다.

따라서 에이전트 시스템에는 다음과 같은 정책이 필요하다.

- 어떤 관찰 결과를 원문으로 유지할 것인가
- 무엇을 요약하고 무엇을 버릴 것인가
- 어떤 정보는 외부 저장소에서 다시 검색할 것인가
- 여러 요청의 캐시를 어떻게 배치하고 재사용할 것인가
- 제한된 GPU 메모리에서 어떤 요청을 먼저 처리할 것인가

이것은 프롬프트 작성만으로 해결되는 문제가 아니다. 캐시, 스케줄링, 메모리 할당, 데이터 이동과 장애 복구가 함께 얽힌 시스템 설계 문제다.

## 외부 지식은 KV 캐시와 다른 층의 메모리다

RAG, 지식 그래프, 온톨로지, LLM 위키와 같은 기술도 결국 유한한 컨텍스트에 어떤 정보를 넣을 것인지 결정한다. 다만 이들을 GPU의 KV 캐시 관리와 같은 것으로 보면 안 된다.

- KV 캐시는 현재 추론 요청의 Attention 계산을 재사용하기 위한 런타임 상태다.
- RAG와 지식 그래프는 모델 밖의 지식에서 필요한 정보를 골라 컨텍스트를 구성한다.
- 에이전트 하네스는 도구, 상태, 관찰 결과와 실행 정책을 관리한다.

서로 다른 계층의 기술이지만 공통 질문은 있다.

> 유한한 자원 안에서 지금 가장 필요한 정보는 무엇인가?

외부 지식 시스템이 관련 문서만 선택해 주면 모델에 불필요한 전체 문서를 넣지 않아도 된다. 이는 모델의 컨텍스트 예산을 아끼고 결과의 근거를 명확하게 만든다. 내가 만든 [Notion 개인 지식베이스](/blog/notion-local-rag-knowledge-base/) 역시 이 문제를 검색과 출처 추적으로 풀어 본 프로젝트였다.

## 피지컬 AI는 시스템 지식을 더 요구한다

피지컬 AI로 범위를 넓히면 시스템 프로그래밍의 필요성은 더 분명해진다. 로봇과 자율 시스템은 모델의 답변만 생성하지 않는다. 센서에서 데이터를 읽고, 제한 시간 안에 판단하며, 액추에이터를 제어해야 한다.

이 환경에서는 다음 문제가 직접 제품의 품질과 안전성으로 이어진다.

- 카메라와 센서 데이터의 I/O 처리
- CPU, GPU, NPU 사이의 데이터 이동
- 실시간에 가까운 지연시간과 스케줄링
- 여러 작업이 동시에 실행될 때의 동기화
- 메모리 복사와 버퍼 관리
- 장치 드라이버와 운영체제 인터페이스
- 장애 발생 시 안전한 복구

클라우드 LLM에서 수백 밀리초의 지연은 불편함으로 끝날 수 있지만, 물리 장치를 제어하는 시스템에서는 결과가 달라질 수 있다. 모델의 정확도만큼 실행 시간의 예측 가능성과 시스템의 안정성이 중요하다.

## 시스템 프로그래밍에서 무엇을 배우는가

시스템 프로그래밍에서는 C 코드가 실행 가능한 프로그램이 되는 과정을 배운다. 컴파일과 어셈블, 링킹, 로딩을 거쳐 프로세스로 실행되는 과정이다. 이 흐름을 따라가면 프로그램이 사용하는 자원이 더 이상 추상적으로 보이지 않는다.

- 실행 파일과 라이브러리는 어떻게 연결되는가
- 프로세스의 주소 공간은 어떻게 구성되는가
- 가상 메모리는 물리 메모리와 어떻게 연결되는가
- 캐시와 지역성은 왜 성능을 바꾸는가
- 동적 할당기는 단편화와 어떻게 싸우는가
- 여러 스레드와 프로세스는 어떻게 자원을 공유하는가
- 시스템 호출은 사용자 프로그램과 운영체제를 어떻게 연결하는가

이 개념들은 LLM 시스템에도 그대로 등장한다. 모델 서버의 메모리 부족, 단편화, 데이터 복사, 스케줄링, 동시성 문제를 이해하려면 프레임워크의 API만 알아서는 부족하다.

프레임워크와 모델은 빠르게 바뀐다. 반면 메모리 계층, 가상 메모리, 지역성, 동기화와 같은 원리는 수십 년 동안 시스템의 기반으로 남아 있다. 표면적인 코드 작성 방식은 자동화되고 있지만 코드가 실행되는 물리적 공간은 사라지지 않았다.

## 개발자의 역할은 코드 밖으로 확장된다

AI 시대의 개발자가 모든 코드를 직접 타이핑할 필요는 점점 줄어들 수 있다. 하지만 좋은 시스템을 만들기 위해 해야 할 일은 여전히 남는다.

- 해결할 문제와 성공 기준을 명확히 정의한다.
- 모델의 출력을 검증할 평가 체계를 만든다.
- 도메인 데이터와 도구를 안전하게 연결한다.
- 비용, 지연시간, 정확도 사이의 트레이드오프를 결정한다.
- 장애를 관찰하고 원인을 재현할 수 있게 만든다.
- 하드웨어와 운영체제의 제약 안에서 서비스를 최적화한다.

최근 AI 제품에서 주목받는 Forward Deployed Engineer 같은 역할도 이 변화와 맞닿아 있다. 특정 모델 하나를 만드는 것보다 실제 도메인과 데이터, 기존 시스템에 AI를 연결하고 끝까지 작동하게 만드는 능력이 중요해지고 있다.

개발자의 역할은 “코드를 작성하는 사람”에서 “AI가 현실의 제약 안에서 올바르게 작동하도록 시스템을 설계하는 사람”으로 확장되고 있다. 그 과정의 중심에는 자원과 메모리에 대한 이해가 있다.

## 마치며

코딩 에이전트가 발전했다고 해서 시스템 프로그래밍의 가치가 줄어드는 것은 아니다. 오히려 AI가 더 긴 컨텍스트를 다루고 더 많은 도구를 사용하며 물리 세계까지 연결될수록, 그 아래의 메모리와 실행 환경을 이해하는 능력이 중요해진다.

KV 캐시는 연산과 메모리의 교환이고, HBM과 오프로딩은 메모리 계층의 문제이며, 에이전트 서빙은 스케줄링과 자원 관리의 문제다. 피지컬 AI는 여기에 I/O, 동시성, 실시간성과 안전성까지 더한다.

그래서 내 결론은 간단하다.

> 개발자는 여전히 필요하고, 시스템 프로그래밍은 여전히 공부할 가치가 있다.

AI가 코드를 대신 작성할수록 개발자는 코드가 어떤 자원 위에서 어떻게 실행되는지 더 깊이 이해해야 한다. 자동화되는 것은 타이핑의 일부이지, 시스템을 이해하고 선택의 책임을 지는 일까지는 아니다.
